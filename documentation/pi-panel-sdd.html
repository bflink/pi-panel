1. Introduction

1.1 Purpose

This Software Design Description (SDD) records how Pi Panel is structured and how its implemented parts collaborate. It is intended to support maintenance, review, testing, and future feature design.

1.2 Product scope

Pi Panel is a single-process graphical application running on a Raspberry Pi 5. It provides:

  • Control of an Explorer HAT Pro onboard LED.
  • Debounced input from a physical button connected to Explorer HAT Input 1.
  • Voltage acquisition from Explorer HAT Analog 1.
  • Conversion of thermistor voltage into degrees Fahrenheit.
  • Display of LED state, voltage, temperature, and recoverable measurement errors.

1.3 Out of scope

  • Network services, remote APIs, user accounts, and persistent storage.
  • Automatic service startup at boot.
  • Closed-loop temperature control or safety interlocks.
  • Automatic thermistor calibration or sensor identification.

1.4 Design principles

  • Keep hardware access behind narrow C++ abstractions.
  • Keep QML declarative and free of hardware details.
  • Use timer-driven work on the Qt event thread for the current small workload.
  • Convert hardware failures into explicit UI state or controlled termination.
  • Make pure logic independently testable without Raspberry Pi hardware.

2.2 Hardware constraints

ResourceConstraint
LEDExplorer HAT LED 2 maps to BCM GPIO 17.
ButtonExplorer HAT Input 1 maps to BCM GPIO 23 and is active-high.
Input biasThe HAT buffer prevents Pi internal bias from controlling the external input; an external pull-down is required.
ADCADS1015 at I2C address 0x48; Analog 1 maps to ADC channel 3.
ThermistorDefault model assumes 10 kΩ NTC, β=3950 K, 25°C nominal, and a 3.3 V divider.

2.3 Software constraints

  • Linux with libgpiodcxx and the Linux I2C device API.
  • Qt 6 Core, Gui, Qml, and Quick.
  • C++20 with compiler warnings treated as errors.
  • The application user requires access to GPIO and the selected /dev/i2c-* device.
  • Only one process may own the requested GPIO lines.

3. Architecture

3.1 Architectural style

The application uses a small layered, event-driven design. QML is the presentation layer, LedViewModel is the presentation boundary, controllers contain device-oriented behavior, and services perform operating-system I/O.

┌─────────────────────────────────────────────┐ │ Presentation: Main.qml │ │ Controls, labels, bindings, error messages │ └──────────────────────┬──────────────────────┘ │ Qt properties/signals ┌──────────────────────▼──────────────────────┐ │ View model: LedViewModel │ │ UI state, commands, exception translation │ └──────────────┬───────────────────┬──────────┘ │ │ ┌──────────────▼──────────┐ ┌─────▼───────────────┐ │ LedController │ │ Thermistor │ │ LED/button semantics │ │ Pure conversion │ └──────────────┬──────────┘ └─────────────────────┘ │ ▲ ┌──────────────▼──────────┐ ┌────┴────────────────┐ │ GpiodService │ │ Ads1015 │ │ Linux GPIO adapter │ │ Linux I2C adapter │ └─────────────────────────┘ └─────────────────────┘

3.2 Dependency direction

  • QML depends on the view-model contract, not controller types.
  • The view model depends on controller and conversion objects by reference; main.cpp owns their lifetime.
  • LedController depends on IGpioService, allowing a mock implementation in tests.
  • Thermistor has no Qt or hardware dependency.
  • Ads1015 and GpiodService are Linux-specific boundary adapters.

3.3 Concurrency model

The current application is single-threaded at the application level. Both timers execute callbacks on the Qt event thread. ADC conversion includes short sleeps while waiting for hardware, bounded by a 100 ms timeout.

4. Component Design

4.1 Lifetime and ownership

main.cpp constructs objects in dependency order: LedController, Ads1015, Thermistor, then LedViewModel. They remain on the stack until the Qt event loop exits. The view model stores references, so it cannot outlive those dependencies.

4.2 Resource acquisition

GPIO lines are requested during GpiodService construction. The ADC file descriptor is opened lazily on the first read and closed by Ads1015 destruction. Copying Ads1015 is disabled to prevent duplicate descriptor ownership.

5. Interfaces and Contracts

5.1 Internal C++ interfaces

OperationContract
IGpioService::setLineValueWrite a logical value to a requested output line; may throw on OS/hardware failure.
IGpioService::getLineValueRead a requested input line; may throw on OS/hardware failure.
LedController::toggleWrite the inverse output and update stored state only after the write succeeds.
ButtonDebouncer::updateReturn true only when a stable transition into pressed state reaches the debounce interval.
Ads1015::readVoltageAccept channels 0–3; return non-negative volts; throw on invalid channel, I/O failure, or timeout.
Thermistor::temperatureFahrenheitRequire voltage strictly between zero and supply; return beta-model temperature.

5.3 External interfaces

  • GPIO character device through libgpiodcxx.
  • Linux I2C device through open, ioctl(I2C_SLAVE), read, and write.
  • Qt platform plugin through the selected desktop environment.
  • Process environment variables for thermistor and I2C configuration.

6. Dynamic Behavior

6.1 Startup sequence

QGuiApplication
  → register POSIX signal handlers
  → construct GPIO/LED, ADC, thermistor, and view model
  → seed ButtonDebouncer from current Input 1 state
  → connect 5 ms and 200 ms timers
  → load Main.qml with ledViewModel initial property
  → take initial analog sample
  → start timers and enter Qt event loop

6.2 Physical button sequence

GPIO 23 high
30 ms stable
toggle()
QML notified

Raw changes restart the debounce interval. The stable press transition returns true once. Stable release is recorded but returns false, preventing a second toggle.

6.3 Analog sample sequence

QTimer timeout
  → LedViewModel::sampleAnalogInput()
  → Ads1015::readVoltage(channel 3)
  → update voltage and analog status
  → Thermistor::temperatureFahrenheit(voltage)
  → update temperature and conversion status
  → Qt signals refresh QML bindings

6.4 Shutdown sequence

SIGINT, SIGTERM, or SIGHUP sets a signal-safe flag. The next 5 ms timer callback calls application.quit(). After the event loop returns, timers stop and the LED is explicitly turned off. Object destructors then release I2C and GPIO resources.

7.3 Persistence

The application has no persistent runtime data. Configuration is supplied at process launch, and measurements exist only in memory. A restart resets LED state, availability state, and sampled values.

8. Reliability and Quality Attributes

8.1 Error policy

FailureResponseImpact
LED command failureEmit operationFailed; do not emit state-changed.Application remains active.
ADC open/read/write/timeoutSet analog unavailable and expose message.LED remains usable; conversion is skipped.
Invalid thermistor voltageSet temperature unavailable and expose message.Raw voltage remains visible.
GPIO polling failureLog and exit with status 1.Application terminates and performs normal cleanup.
Invalid startup configurationTop-level catch logs and returns 1.Application does not start.

8.2 Timing and responsiveness

  • Button poll: 5 ms; accepted press latency is normally 30–35 ms plus event-loop scheduling.
  • Analog update: 200 ms nominal period.
  • ADC wait: bounded at 100 ms, but runs on the UI thread and can temporarily delay rendering.

8.3 Safety and security considerations

  • The software is monitoring/control software, not a certified safety system.
  • Hardware voltage limits and Explorer HAT ratings remain external constraints.
  • Device access relies on Linux user/group permissions; the application does not require embedded credentials.
  • Environment input is parsed at startup; malformed numeric values fail closed by preventing startup.

9. Build and Deployment Design

9.1 Build products

TargetContents
pi_panel_coreADC, debounce, GPIO, LED, and thermistor C++ implementation.
pi_panelQt executable, view model, and embedded QML module.
pi_panel_testsGoogleTest executable linked to the core library.

9.2 Build dependencies

  • CMake 3.20 or newer and a C++20 compiler.
  • Qt 6 Core, Gui, Qml, and Quick development packages.
  • pkg-config and libgpiodcxx.
  • GoogleTest 1.14 fetched by CMake when configuring tests.

9.3 Runtime environment

  • /dev/gpiochip0 with access to lines 17 and 23.
  • /dev/i2c-1 or configured replacement, with ADC address 0x48.
  • A Qt-supported display. The checked-in profiles use the Pi Xwayland display or PuTTY-forwarded X11.

9.4 Deployment model

The executable is launched interactively from VS Code or a terminal. No systemd unit, installer, update agent, or automatic boot startup is part of the current design.

10. Verification and Evolution

10.1 Automated verification

AreaVerified behavior
LED controllerInitial state, toggle transitions, pin values, explicit off, destructor cleanup, button polarity, custom pins.
DebouncerStable press, ignored early press, bounce reset, release behavior, repeated cycles.
ThermistorNominal midpoint, expected direction for both orientations, range rejection, observed 1.70 V room reading.

10.2 Current test gaps

  • No automated I2C transaction tests for Ads1015.
  • No unit tests for LedViewModel signal and error-state transitions.
  • No automated QML interaction or screenshot tests.
  • No integration test covering real GPIO and ADC hardware together.

10.3 Extension guidance

  • Add new hardware behind an interface when practical, preserving testability.
  • Keep physical units explicit in names and contracts.
  • Move blocking I/O off the UI thread if sampling becomes slower or more complex.
  • Add persistent configuration only when runtime environment variables become insufficient.
